# Materials and lightmaps

Sources: static analysis of `gfx_d3d_x86_s.dll` (v1.0) with REA 6.7.0 + Ghidra 12.1.4, checked against the
shipped `materials/*` files and the game's own shader sources (`materials/shaders/lib/*.hlsl`).

## Material file (`materials/<name>`, binary, little endian)

Loaded through `materials/%s` (`FUN_1001c7a0`) and fixed up in `FUN_1001c540`.
Every offset field is relative to the start of the file and is turned into a pointer at load time.

| Offset | Type | Field | Status |
|---|---|---|---|
| 0x00 | uint32 | offset of material name | observed (relocated) |
| 0x04 | uint32 | offset of a second name (the reference image; equals the colorMap image in the samples) | relocated; meaning inferred |
| 0x08–0x2b | – | sort key and other flags | mostly not decoded; **byte 0x0d = draw sort byte** (1.3 DLL: the loader copies the 0x44-byte header verbatim, 0x100171a0, and nothing rewrites it; the table sort 0x10016ae0 orders by it ascending, then by techset allocation address = techset first-load order, 0x1001c280 allocates 0x8c bytes per techset; shipped values: 3 default/opaque (2120 files), 4 sky, 5 sun, 7 backdrops, 8-16 decals, 19-23 alpha, 25-26 effect blends, 27 additive (518), 28); byte 0x0c: bit 8 sky (1.0 DLL FUN_10002a00), bit 4 no marks (1.3 DLL FUN_100157f0); bytes 0x0e / 0x0f: atlas rows / columns (0x10017580, 0x1003fa60) |
| 0x2c | uint32 | state bits word 0 (blend: mtlDestBlend 0xf0, mtlBlendOpAlpha 0x7000000, mtlSrcBlendAlpha 0xf0000, mtlDestBlendAlpha 0xf00000, mtlCullFace 0xc000, colour write 0x8000000 / 0x10000000, mtlFog 0x20000000) | statemap variable table 1.3 DLL 0x1018fd80 |
| 0x30 | uint32 | state bits word 1 (mtlDepthTest 0xe, mtlDepthWrite 0x1, mtlPolygonOffset 0x30, mtlStencil 0xc0, stencil func / ops 0xe0000 / 0x700 / 0x3800 / 0x1c000) | same table |
| 0x34 | uint16 | texture count | observed (loop bound) |
| 0x36 | uint16 | constant count | observed (loop bound) |
| 0x38 | uint32 | offset of technique-set name (`materials/techniquesets/<name>.techset`) | observed |
| 0x3c | uint32 | offset of the texture table | observed (relocated) |
| 0x40 | uint32 | offset of the constant table | observed (relocated) |

Texture entry (12 bytes):

| Offset | Type | Field |
|---|---|---|
| 0 | uint32 | offset of the sampler name (`colorMap`, `detailMap`, `normalMap`, `specularMap`, …), hashed at load time |
| 4 | uint8 | sampler state (inferred) |
| 5 | uint8 | semantic: 2 = color (also used by `detailMap`), 3 = normal, 4 = specular, 5 = water. These values are compared in the loader; the names come from the data |
| 6 | uint16 | padding (always 0 in samples) |
| 8 | uint32 | offset of the image name (`images/<name>.iwi`). For semantic 5 it is an offset to a water description instead |

Images whose name starts with `$` are built-in (generated by the engine, for example `$white`).

Constant entry (20 bytes): `uint32 nameOffset; float value[4]` (for example `detailScale = 8 8 0 0`).

## Lightmaps (lump 1 of `.d3dbsp`)

Each 4 MiB lightmap holds four images back to back. Their sizes come from `FUN_10001ff0`:

| Part | Size | Bytes/px | Shader sampler (from `globals.hlsl`, `lightmap.hlsl`) |
|---|---|---|---|
| 0 | 512 × 512 | 4 (B,G,R,A) | `lightmapSamplerR`: 4 lighting coefficients for red |
| 1 | 512 × 512 | 4 | `lightmapSamplerG` |
| 2 | 512 × 512 | 4 | `lightmapSamplerB` |
| 3 | 1024 × 1024 | 1 | `lightmapSamplerSun`: sun visibility |

The game's shader computes `lightmapDiffuse.c = dot(coeffs_c, weights)`. Here `weights` is sampled from the
engine-generated `$lightmapweights` texture at the normal-map sample. Sun light is then added as
`sunVisibility × lightColor0 × max(0, N·L)` (`lightmap.hlsl`, `phong.hlsl`).

### `$lightmapweights` (32 × 32, ARGB8888), built in `FUN_1000fef0` and `FUN_1000fdd0`

For texel `(i, j)`: `x = 2(i + 0.5)/32 − 1`, `y = 2(j + 0.5)/32 − 1`. If `x² + y² > 1`, the vector is normalized.
`z = sqrt(1 − x² − y²)`. The four weights, stored as bytes 0..3 of each texel (`round(w × 255)`), are:

1. `t = atan2(y, x) × 3/(2π) − 0.75`, wrapped into `[0, 3)`.
2. `t ∈ [0,1)`: `(w1, w2, w3) = (1 − t, t, 0)`. `t ∈ [1,2)`: `(0, 2 − t, t − 1)`. `t ∈ [2,3)`: `(t − 2, 0, 3 − t)`.
3. `w0 = clamp(1 − angle(z) × 1.0467734, 0, 1)`. The angle function (`FUN_100f8d90`) is inferred to be `acos`;
   the constant is `1 / acos(1/√3)`.
4. `w1..w3 *= (1 − w0)`.

So a flat normal map gives weights `(1, 0, 0, 0)`: only byte 0 of each coefficient texel is used. The renderer must
keep the same byte order for coefficient and weight textures.

Sun direction: the forward vector of the worldspawn `sundirection` angles (pitch, yaw, roll) points **towards** the sun.
With this convention the lightmap sun-visibility shadows line up with the sun-lit faces (checked visually on `toujane`).

When `r_optimizeLightmaps` is 2, the renderer instead merges the lightmaps into one RGBA image per lightmap,
built from part 0.

Lightmap index 31 on a triangle soup means "no lightmap".

## Alpha test (1.3 DLL 0x1003c8c0..0x1003ca29)

mtlAlphaTest lives in state word 0 (file 0x2c; value table 0x1018f7d8). Bit 0x800 set = test off (Always). Otherwise bits 0x3000
choose the D3D function and reference: 0x1000 GT0 = GREATER 0, 0x2000 LT128 = LESS 0x80, 0x3000 GE128 = GREATEREQUAL 0x80 (the
function falls through to GREATEREQUAL for any other value). The test belongs to the material, not to the technique name.
Shipped use: `phong_alphatest` is GE128 for 59 materials, LT128 for the 48 `foliage_masked@*` ones (no shipped map or model references them), GT0 for one; the `*_detail` and
`*_spec_detail` variants have GT0 too (e.g. `toujane_decal_rug1`), and blend / effect materials commonly have GT0 or GE128 on.

The test acts on the shader's output alpha, here quantized to 8 bits. iw2view applies the material's function in fs_main,
fs_spec and fs_dlight. The multiply techniques are excluded because their output alpha is a constant 1, which GT0 / GE128 pass.
The depth-only "build floatz" technique keeps its own fixed reference (`lib/float_z_build_alphatest.hlsl`).

## Texture sampler state (1.3 DLL 0x1003ddc0)

Byte 4 of each texture entry. Bits 0-1 give min/mag filter, bits 2-3 the mip filter, both through {NONE, POINT, LINEAR,
ANISOTROPIC} (0x10190714); bits 4/5/6 clamp U/V/W, clear = wrap. Mip NONE samples only level 0. A filter of ANISOTROPIC
(0x1003dc90) uses r_anisotropy limited by the device, the POINT / LINEAR values never do.

A byte whose low four bits are zero (0x1003dec6) has the default ORed in: `{1, 2, 6, 0xa, 0xb}[r_textureMode]` (table
0x101906b0; nearest, linear, bilinear, trilinear, anisotropic). r_textureMode registers with default "bilinear" (byte 6: LINEAR
min/mag, POINT mip, no anisotropy; 0x1000abb6), and the shipped `configure.cfg` and `safemode.cfg` set the same value. r_anisotropy is
an int 2..16 with default 8 (0x1000abd1). This covers colorMaps too: for example `egypt_rug1` (state 0x30) clamps U and V, and most
shipped colorMaps have state 0 and so follow r_textureMode.

iw2view reads both dvars from the menu cvar store (`--cvar r_texturemode=anisotropic` for a shot). Both register with flags
0x2001, so they are archived in the player profile. The original's graphics page applies the filter row only through its Apply
button and restart, and `ui/options_graphics.menu` hides Apply while a level runs. openiw2 applies a change at the next frame, so
as a deliberate deviation a write to ui_r_texturemode also sets r_texturemode at once, in a level as well as in the main menu.

Code samplers have fixed bytes in the lookups 0x10038dd0 / 0x10039030; floatZ (code sampler 0x15) is 0x31: point, no mip, clamped.

The alpha the test sees from a USE_ALPHA technique is the colour map's alpha times the vertex alpha (shade library: the textured
diffuse is multiplied by the vertex colour and the lightmap / light-probe shaders write that product's alpha; iw2view
`base = tex0 * in.color`, `assets::shaderOutputAlpha`). The shipped mips carry their own alpha. Measured example, the striped
blanket on the bench in decoytown (`egypt_rug3`, GE128, colour map `egypt_rug3_c`, DXT5 256 × 128): the alpha averages 181/255 at
every level; level 0 is noisy (124..255, a third of the texels in 128..159, 0.6 % below 128), level 1 and smaller are smooth
(131..253 at level 1, 164..199 at level 3). Under opaque vertices the product is ~0.71 and passes everywhere. The map paints the
blanket's vertex alpha from 255 along the top edge of its hanging face down to 41 at the lower edge, so the product crosses 128/255
inside the lower half of that face: there level 0 gives a dissolved cut that moves with the sampling position, level 1 a clean line.
At the player's distance the LOD across the face lies between 0 and 0.5 (measured +0.1..+0.3 in a 1280 × 800 view), so with the
default point mip filter a small move can switch the face between the two looks. This follows from the sampler and alpha-test rules
read from the renderer and from the shipped shaders and map; it has not been compared against the original's picture. Forced
anisotropy keeps level 0 in use at more angles. No D3DSAMP_MIPMAPLODBIAS call exists in the renderer, so there is no texture LOD bias.

## Multisampling (r_aaSamples, deliberate deviation in the default)

The original registers r_aaSamples with default 1 (0x1000b212), and its graphics menu offers Off, 2x and 4x. openiw2 defaults to 4 to
remove the alpha-test shimmer described above; this is not the original's look, and "Off" in the menu restores single sampling.
The value is read when the renderer starts, so a change applies at the next start. It is lowered when the device lacks the count.

The scene passes render into multisampled colour and depth targets and resolve into the scene image; $floatz, the screen filters and the
2D pass stay single-sampled, and the post-sun copy is made from a resolve. This alpha to coverage is an openiw2 addition with no
counterpart in the original: when more than one sample is active, the AlphaTest pass enables it. GE128 materials output
`saturate((a - 128/255) / fwidth(a) + 0.5)` as coverage and are not discarded; other functions keep their test and output 1. On a
noisy alpha the ramp is wide, so a dissolved edge comes out as partial coverage (a dither) rather than as whole-pixel holes.

The scene pass is interrupted before the blended passes for the post-sun copy (made whenever glow is on or an effect reads the copy)
and resumed with LOAD, so its first part stores its colour samples (RESOLVE_AND_STORE) and its depth (`assets::scenePassStores`).
Storing the resolve alone, or DONT_CARE for the depth, leaves the resumed pass reading undefined sample memory: in a 1280 × 800
4-sample shot of the decoytown bench the alpha-tested surfaces (the blanket, the floor rugs, the view model) were missing in 3 of 5
renders before this rule and in none of 5 after it; with one sample the depth of the resumed pass was undefined the same way.

## Polygon offset (1.3 DLL 0x1003d230)

mtlPolygonOffset values "0" / "1" / "2" = 0 / 0x10 / 0x20 (value list 0x1018fab8); the statemaps pass it through.
When the level changes: D3DRS_SLOPESCALEDEPTHBIAS (0xaf) = level · r_polygonOffsetScale and D3DRS_DEPTHBIAS (0xc3) =
level · r_polygonOffsetBias · 2⁻¹⁶ (0x1019be30); without slope-scale support only DEPTHBIAS, doubled. Dvars
(0x1000adaa / 0x1000adce): r_polygonOffsetScale default −1 (−4..4), r_polygonOffsetBias default −1 (−16..16).
iw2view: offset pipelines with the slope factor and the constant added to the clip depth in `vs_main`.

## Draw order (1.3 DLL 0x100247d0, 0x10024900, 0x10025490)

One scene list holds world surfaces, static models, dynamic models and marks. Its key is material rank << 21 | layer << 16 | entity << 4 |
record type (writer 0x100247d0), sorted ascending once per frame (0x10024900). Material rank is the table order of 0x10016ae0: sort byte 0x0d,
then technique set first-load order. Layer is the lightmap index, 31 for none. The builder 0x10025490 walks that same list three times: technique
type 1 (sky, 0x10025565), type 6 (lightmap no fog, 0x10025570), then, after the sun and the post-sun copy, type 0x18 or 0x15 (emissive, 0x10025671).
A surface is drawn only by a walk its technique set has a technique for: `effect*` sets have only emissive techniques, all others shipped
with world surfaces only lit ones. So opaque, alpha-tested and blended lit materials interleave purely by sort byte, and blending comes
after the opaque surfaces only because its byte is higher.

The blend comes from state word 0, not from the technique set name, because every scene state map passes it through: source factor bits 0-3,
destination bits 4-7, operation bits 8-10 (0 Disable, 1 Add), factors 1 Zero, 2 One, 3 SrcColor, 5 SrcAlpha, 6 InvSrcAlpha. Both
`effect_multiply_nofog` materials multiply (Zero / SrcColor), and 9 of the 22 `unlit_blend` materials are additive. Depth write follows the blend
(nofog.sm: Enable only for mtlBlendOp Disable), and all shipped materials test LessEqual.

Key details. Technique sets are first allocated at their first use (0x1001c280 on a miss of the name hash 0x101d82e8). The material and technique tables
restart empty at every level start and at vid_restart (0x100131e0 -> 0x100177b0). The soup loader 0x10002a00 registers each soup's material in soup order
during LoadWorld, which CG_Init calls first (0x4a2aac in the patch 1.3 SP executable). The table is sorted by an unstable introsort (0x10017c10), so materials equal in
sort byte and technique set have no defined order. Layer is the lightmap index, 31 for none; entity is 0x800 + sort group for world soups (sort group 0x10002800:
first appearance of a vertex range within the material), 0x7ff for static models, the reference entity slot for dynamic and brush models.
Marks use 0x800 + a per-frame counter. Effect sprites sort after every other record (docs/spec/effects.md).

Walks. The list is walked for technique type 1 (sky), type 6 (lit surfaces, water included: `water.techset` has a lit technique only, at its material's rank), then the
sun, the post-sun copy, one walk per dynamic light, then the emissive walk. Dynamic lights (0x10015210, 0x10014fe0, emitted at 0x10025643) walk a reversed copy of the list
filtered by radius with technique type 0x12 over every surface whose technique set has a "pointlight" technique, including the blended ones: `l_point_blend` scales the light by
the surface alpha, and state map `additive_nofog.sm` tests Equal over opaque and LessEqual over blended surfaces.

iw2view: `drawListWalk` follows this for world, brush-model, static and dynamic surfaces, with the post-sun copy before the lights. The light walks take every list surface with a pointlight technique, models included (`receivesDynamicLight`). The l_point pass perturbs the normal with the material's `normalMap` for every `phong_*` technique set (lib/normalmap.hlsl: x from alpha, y from green; the flat `$identitynormalmap` leaves the interpolated normal). World vertices carry the frame in the bsp, models in the surface file, and skinned models rotate it with the first bone, as the normal. `phong_*_detail` materials use `l_point_dtl`, which adds the detail map to the colour as the base pass does. World surfaces of one material and
lightmap form one batch, so sort groups have no effect; surfaces equal in sort byte and technique set are drawn in first-use order of the material (deliberate
deviation: the original's order is unspecified). TODO(spec): the order of first use across static models and precached assets relative to soups could not be
determined; iw2view registers static models after the soups. TODO(spec): `additive_nofog.sm` names the source factor InvDestAlpha, while iw2view adds with One / One and
Equal is approximated by LessEqual; how the destination alpha behaves in a lit frame is not analysed. The mark layer source is not traced; marks use layer 31.

Coplanar layers (deliberate deviation). The original's depth buffer is D3DFMT_D24S8 (0x1001159c, 0x10022ce2). iw2view uses a 32-bit float
depth because Apple GPUs have no 24-bit unorm format, so differently triangulated faces in one plane differ by rounding in tiles of the GPU's
interpolation and a later surface loses LessEqual in blocks that change with the camera (trainyard: snow `stalingradwinter_snow02a` on the roof
`mtl_hill400_roof_01`). A world surface that does not write depth is moved 2^-19 of clip depth toward the camera, an eighth of one polygon offset
level, so that it wins the tie with any coplanar surface drawn earlier, which is the outcome LessEqual asks for. Coplanar depth-writing surfaces are not changed.

## Face culling (1.3 DLL 0x1003cb13)

mtlCullFace = bits 14–15 of state word 0 (file 0x2c, mask 0xc000; values None / Back / Front = 0x4000 / 0x8000 /
0xc000, table 0x1018fa10); D3DRS_CULLMODE from {0, D3DCULL_NONE, D3DCULL_CCW, D3DCULL_CW} (0x10190704), i.e. Back
culls counter-clockwise (back) faces with D3D's clockwise front faces. 371 of the shipped materials sampled use Back.
iw2view: pipelines per pass × polygon offset × cull, front face clockwise (the opposite winding renders the toujane
houses inside out). The mark entry 0x10024320 only copies vertices into a type-1 draw record under the mark's material, so culling and polygon offset are the material's state.
